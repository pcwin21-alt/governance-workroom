# 거버넌스 워크룸 MVP

청년참여기구의 회의·정책제안·피드백·제출·후속 경과를 하나의 흐름으로 관리하는 합성 데이터 기반 MVP입니다.

> 실제 행정안전부 서비스, 실제 자문단, 실제 청년위원, 실제 정책 자료와 무관한 데모입니다. 실제 개인정보를 입력하지 마세요.

## 실행

필수 환경: Node.js 20 이상 (외부 패키지 설치 없음)

```powershell
npm run seed:reset
npm start
```

브라우저에서 `http://localhost:4173`을 엽니다.

## 공개 소개·도입 흐름

로그인하지 않은 방문자는 아래의 공개 경로에서 서비스 적합성을 먼저 확인합니다.

| 경로 | 역할 |
| --- | --- |
| `/` | 회의→제안→제출 경과를 보여 주는 소개 홈 |
| `/how-it-works` | 전체 운영 흐름 |
| `/use-cases` | 역할·기구별 사용 장면 |
| `/governance-and-security` | 개인정보·권한·AI 경계 |
| `/pilot` | 개인정보를 받지 않는 파일럿 준비 점검 |
| `/login` | 초대받은 사용자의 데모 로그인 |
| `/join/:token` | 초대 링크 수락, 최소 가입 정보 등록, 소속 승인 대기 |

`/pilot`은 현재 실제 이름·이메일·연락처를 저장하거나 외부로 전송하지 않습니다. 실제 파일럿 접수는 수신 채널, 문의 처리 동의, 보존기간을 확정한 뒤 별도 연동해야 합니다.

## 이용 구조

무기한 무료 워크룸은 제공하지 않습니다. 공개 영역은 템플릿과 합성 데모를 확인하는 체험 범위이며, 실제 기구의 다기관 운영·저장·활동 리포트·운영 지원은 기관 계약 또는 후원 좌석에 포함됩니다.

| 이용 방식 | 범위 |
| --- | --- |
| 템플릿·체험 | 공개 템플릿·합성 데모 확인. 실제 개인정보·기관 자료·운영 기록 입력 금지 |
| 기관 계약 | 테넌트, 저장·아카이브, 활동 리포트, 합의된 지원 범위를 계약별로 설정 |
| 후원 좌석 | 지자체·재단·기업·연구소 등이 좌석·기간을 후원하는 기관 계약형 이용. 참여기구가 기록과 권한의 주체 |

운영사 콘솔에서 이용 방식, 상태, 후원 주체, 좌석 수, 이용 기간, 지원 범위를 기록할 수 있습니다. 이 MVP에는 결제, 계약 체결, 청구, 후원금 정산, 자동 갱신·만료 차단이 없습니다.

## 개인 데이터와 참여기구 데이터

좌측 메뉴에서 두 데이터를 분리합니다.

| 메뉴 | 다루는 데이터 | 수정 권한 |
| --- | --- | --- |
| `내 정보·데이터` | 로그인한 사람의 이름, 선택형 연령대·직업·거주 지역, 비밀번호, 내 데이터 요청 | 해당 사용자 본인 |
| `참여기구 데이터 관리` | 기구명, 기수, 소속기관·구분, 대표, 임기, 근거 규정, 로고, 보도자료 피드, 기관 홈페이지·청년정책·참여 안내 바로가기 | 해당 참여기구의 위원장만 |

참여기구 데이터는 모든 구성원이 읽을 수 있지만, 운영사 관리자·간사·일반위원도 수정할 수 없습니다. 개인 프로필에는 전체 생년월일, 민감정보, 개인 연락처를 입력하지 않습니다.

## 파일럿 문의와 운영사 알림

`/pilot`에서 기구명, 담당자 이름, 업무용 이메일, 선택형 업무 연락처, 운영 장면과 문의 처리 동의를 받아 도입 문의를 저장합니다. 새 문의는 운영사 관리자 계정의 `운영사 콘솔 → 도입 문의`에 즉시 표시되며, 일반위원·다른 테넌트에는 보이지 않습니다.

외부 이메일 알림은 아래 값을 **배포 환경의 비밀관리 도구**에 설정했을 때만 발송을 시도합니다. 값을 브라우저·소스 코드·감사 로그에 넣지 마세요.

```powershell
$env:RESEND_API_KEY = 're_...'
$env:PILOT_NOTIFICATION_TO = '수신할-운영자@도메인'
$env:PILOT_NOTIFICATION_FROM = '워크룸 <notifications@발신-인증-도메인>'
npm start
```

발송 설정이 없거나 실패하면 문의 자체는 운영사 접수함에 남고, 화면에는 외부 이메일이 미연결 또는 실패로 표시됩니다. Resend에서 발신 도메인과 수신 주소를 설정한 뒤 실제 발송을 별도로 확인해야 합니다. [Resend 이메일 전송 API 문서](https://resend.com/docs/api-reference/emails/send-email)

## 청년 활동가·기관 운영자 통로와 알림

첫 화면과 로그인은 다음 두 통로를 분리해 안내합니다. 이 선택은 권한을 새로 주지 않으며, 실제 접근 범위는 초대된 테넌트 소속과 서버 역할 검사로만 결정됩니다.

| 통로 | 로그인 뒤 첫 과업 | 현재 구현 범위 |
| --- | --- | --- |
| 청년 활동가 | 회의 의견을 정책제안으로 작성하고 기관에 전달 | 제안서 작성자·공동 작성자가 전달 메시지를 남김 |
| 기관 운영자 | 기관 수신함에서 전달 건을 확인하고 운영 답변을 남김 | 위원장·운영·간사 계정의 수신 확인·답변 |

`정책제안 → 기관에 전달 → 기관 확인 → 기관 답변 → 작성자·공동 작성자 알림`이 하나의 테넌트 안에서 작동합니다. 알림은 서버에 사용자별 인앱 알림으로 저장되며, 사용자가 선택해 브라우저 알림을 켜면 **페이지가 열려 있는 동안** 새 알림을 운영체제 알림으로도 표시합니다.

현재는 이메일·카카오·문자 발송, 백그라운드 푸시, 공식 행정결정, 부서별 결재·공문 연동을 구현하지 않았습니다. 이들은 기관의 수신 채널, 동의·보존 기준, 계정·권한 체계가 확정된 뒤 별도 연결해야 합니다.

## 소속기관 보도자료 수집·알림

위원장은 `내 정보·데이터 → 참여기구 정보 수정`에서 소속기관의 **공식 RSS·Atom 피드 주소**를 등록할 수 있습니다. `이슈·공지` 메뉴에서는 현재 수집 상태를 확인하고 `지금 수집`으로 연결을 점검할 수 있습니다.

- 서버가 실행 중인 동안 3시간마다 피드를 확인합니다. 새 항목만 이슈 채널에 추가하며, 같은 제목·원문 링크는 중복 등록하지 않습니다.
- 새 보도자료가 있으면 해당 참여기구의 활성 구성원에게 인앱 알림을 기록합니다. 페이지를 열어 둔 구성원은 기존 브라우저 알림 설정에 따라 운영체제 알림도 받을 수 있습니다.
- 항목마다 원문을 열고, 제목·원문 링크를 브라우저 공유 창 또는 클립보드로 외부 공유할 수 있습니다.
- 수집 주소는 HTTPS 공인 주소만 허용하고, 내부망·localhost·사설 IP·리다이렉트는 차단합니다. 피드 크기는 1MB로 제한합니다.

이 MVP는 RSS·Atom처럼 구조가 있는 공식 피드만 수집합니다. 기관 홈페이지 HTML을 임의로 긁거나, 로그인·캡차·우회가 필요한 사이트를 수집하지 않습니다. 기관별 수집 대상·주기·저작권·공개 범위는 실제 도입 전에 확정해야 합니다.

개발 중 자동 재시작은 다음을 사용합니다.

```powershell
npm run dev
```

## Google 로그인 설정

Google 로그인은 **초대된 워크룸 계정과 같은 이메일**에만 세션을 발급합니다. 임의의 Google 계정으로 새 테넌트나 구성원을 만들지 않습니다.

Google Cloud Console에서 OAuth 웹 클라이언트를 만들고, 다음 값을 실행 환경에 설정하세요. 로컬 기본 리디렉션 URI는 `http://localhost:4173/api/auth/google/callback`입니다. 배포 환경에서는 `GOOGLE_REDIRECT_URI`를 등록한 HTTPS 주소로 명시하세요.

```powershell
$env:GOOGLE_CLIENT_ID = '...apps.googleusercontent.com'
$env:GOOGLE_CLIENT_SECRET = '...'
$env:GOOGLE_REDIRECT_URI = 'http://localhost:4173/api/auth/google/callback'
npm start
```

설정값이 없으면 Google 버튼은 로그인 화면에 표시되지 않고, 기존 데모 로그인을 계속 사용할 수 있습니다.

## 카카오 로그인 설정

카카오 로그인도 동일하게 초대된 워크룸 사용자 이메일에만 연결됩니다. 카카오 디벨로퍼스에서 앱을 만든 뒤 **카카오 로그인 활성화**, **Redirect URI**, **이메일(account_email) 동의항목**을 설정하세요.

```powershell
$env:KAKAO_REST_API_KEY = '카카오 REST API 키'
$env:KAKAO_CLIENT_SECRET = '카카오 Client Secret'
$env:KAKAO_REDIRECT_URI = 'http://localhost:4173/api/auth/kakao/callback'
npm start
```

배포 환경에서는 카카오 디벨로퍼스에 등록한 HTTPS Redirect URI와 `KAKAO_REDIRECT_URI`가 정확히 같아야 합니다. 이메일 제공 동의 또는 이메일 확인이 되지 않은 카카오 계정은 워크룸에 로그인할 수 없습니다.

## 선택형 AI 리포트 검토

기간 활동 리포트는 API 키 없이도 규칙 기반 집계와 다음 행동 제안을 제공합니다. 아래 환경변수를 설정하면 위원장·간사가 생성한 리포트에 한해 **비식별 집계값만** OpenAI API로 보내 운영 회의용 검토 문안을 추가할 수 있습니다.

```powershell
$env:OPENAI_API_KEY = '...'
$env:OPENAI_MODEL = 'gpt-5.6' # 선택
npm start
```

AI 문안은 자동 평가·자동 제출·법적 판단이 아닙니다. 개인별 출결·활동 점수·이름·연락처는 보내지 않으며, 최종 판단과 인계 승인은 사람이 합니다. API 사용량·요금제·보존 조건은 실제 도입 계약에서 별도로 확정해야 합니다.

## 위원회 소개자료·명단 가져오기

위원장은 `구성원·임기 → 기구 자료 가져오기`에서 HWP, HWPX, PDF, XLSX, CSV, TXT 파일(10MB 이하)을 검토용으로 올릴 수 있습니다. 흐름은 다음과 같습니다.

1. 파일을 올리면 기구 정보·명단의 **검토 초안**만 생성합니다.
2. 위원장이 기구 정보와 명단 행을 수정하고, 반영할 행만 선택합니다.
3. `최종 반영`을 누를 때에만 기구 프로필과 구성원 명단에 반영합니다.
4. 이메일이 있는 신규 명단은 `초대 전 등록` 상태로만 만들어집니다. 계정 발급·로그인은 별도의 초대 링크와 가입 승인 뒤에 가능합니다.

CSV·XLSX는 표의 헤더(이름, 이메일, 역할, 임기 등)를 읽어 초안을 만듭니다. HWPX·텍스트 기반 PDF는 읽을 수 있는 텍스트만 참고하며, 스캔 PDF·복잡한 표·구형 HWP는 자동 추출을 보장하지 않습니다. 구형 HWP는 원본을 HWPX·XLSX·텍스트 기반 PDF로 다시 저장하거나 검토 화면에서 직접 입력해야 합니다.

원본은 공개 경로나 일반위원에게 노출되지 않고 로컬 `data/imports`에만 보관됩니다. 검토 초안을 폐기하면 원본도 즉시 삭제하며, 반영 여부와 관계없이 30일 보관기한이 지나면 다음 서버 요청 때 원본을 정리합니다. 이 로컬 정리는 실제 기록물 보존·파기 체계가 아닙니다. 실제 파일럿에서는 기관의 기록물·개인정보 보존기준, 백그라운드 파기 작업, 악성 파일 검사, 암호화 저장소를 별도로 확정해야 합니다.

## 통합 자료 만들기

`자료 아카이브`는 일반 게시판이 아니라 운영 기록을 모으는 테넌트별 드라이브입니다. 목록(스프레드시트)과 미리보기(폴더·카드) 사이를 전환할 수 있으며, 회의·정책제안·이슈·공지·기수 인계·활동 리포트에서 만든 기록을 원본과 분리된 **보관본**으로 넣습니다. 원본 기록은 아카이브 이동·갱신으로 수정되지 않습니다.

- 기본 폴더: 회의·운영 기록, 정책제안, 공지·이슈, 기수 인계, 운영 메모, 기타 자료. 위원장은 폴더를 더 만들 수 있습니다.
- 위원장은 화면 안에서 작성한 메모를 제목·본문이 있는 `메모 파일`로 만들고 폴더에 보관할 수 있습니다.
- 보관본은 폴더 이동, 메모 추가, 최신 원본으로 갱신을 지원합니다. 각 항목에는 실행자, 해당 기수, 시간, 이동·수정·메모 이력이 자동으로 남습니다.
- 회의록·제안서·인계 자료를 보관할 때는 해당 시점의 내용을 읽기용 사본으로 만들므로, 다음 기수도 당시 맥락을 확인할 수 있습니다.

이번 MVP의 드라이브는 **운영 기록과 메모의 구조화 보관**까지입니다. 임의의 바이너리 파일 업로드·다운로드, 실제 이미지 썸네일 생성, OCR, 파일 버전 비교, 악성코드 검사, 기관 기록물 보존 자동판정은 아직 구현하지 않았습니다. 기존 `기구 자료 가져오기`의 문서 업로드는 위원장 검토 초안용이며, 이 드라이브의 범용 파일 저장소와는 분리됩니다.

위원장·간사는 보관 기록 1~25건을 선택해 `회의 결과 정리`, `정책제안 전달문`, `기수 활동자료집` 초안을 만들 수 있습니다. 생성 시점의 제목·본문을 문서 안에 복사해 두므로 이후 원본이 바뀌어도 전달 문서의 근거가 흔들리지 않습니다. `DOCX`는 수정 가능한 문서로 바로 내려받고, `PDF로 저장`은 인쇄 전용 화면을 열어 브라우저의 **인쇄 → PDF로 저장**으로 만들 수 있습니다. 이 MVP는 별도 변환 엔진 없이 한국어가 깨지지 않는 출력 경로를 우선한 것이며, HWP/HWPX 직접 생성과 서버 측 PDF 렌더링은 실제 도입 전 별도 변환·보안 인프라를 검토해야 합니다.

## 합성 시드 데이터

- 행정안전부 2030자문단을 모델로 한 2기·20명 기준 테넌트
- 지난 회의 1건과 예정 회의 2건, 이슈 3건, 정책제안서 2건, 인수인계 자료, 기본 조직도
- 회의·일정은 월간/주간 캘린더에서 확인하며, 참석 응답·운영자 출결 관리·회의록·결정·CSV 내보내기를 제공합니다.
- 위원장은 14일짜리 초대 링크를 만들고 전달할 수 있으며, 가입 신청을 승인한 뒤에만 해당 위원이 로그인할 수 있습니다. 자동 이메일 발송은 연결하지 않았습니다.
- 초대 링크에는 역할·임기·만료일·추가 안내를 담은 메신저/메일용 문구가 함께 생성됩니다. 문구·링크 복사와 기본 메일 앱 열기만 제공하며, 실제 발송·수신 추적은 연결하지 않았습니다.
- 기수 인계는 `계획 → 다음 운영진 초대·승인 → 권한 전환 → 인계 패키지 아카이브` 순서로 진행합니다. 완료 시 이전 의장단·간사는 일반위원 역할로 전환되고, 지정한 다음 위원장·간사에게 역할이 넘어갑니다.
- 기간 활동 리포트는 회의·실제 출결·결정·정책제안·피드백·아카이브를 개인 식별이나 순위 없이 집계해 잘 이어진 흐름·보완 지점·다음 운영 행동을 제안합니다.
- 조직도는 계층형 도식과 전체 위원 표를 함께 제공하며, 구성원은 복수 분과·TF 겸임 배치가 가능합니다. 배치·직책은 구성원별로 명시적으로 회수할 수 있습니다.
- 기본 역할은 위원장·부위원장·운영·간사·분과장·일반위원·외부 검토자이며, 위원장은 기구별 명칭과 관리 범위를 조정할 수 있습니다.
- 내 정보·데이터에서는 참여기구의 대표·업무 연락처·근거 조례·임기·활동 기간·기수·로고를 함께 확인하며, 위원장만 수정할 수 있습니다.
- 위원장은 소개자료·명단을 검토 초안으로 불러온 뒤 행별 포함 여부와 기구 정보를 직접 수정하고 최종 반영할 수 있습니다. 원본을 곧바로 계정·기구 정보로 반영하지 않습니다.
- 테넌트 템플릿, 콘텐츠 검토 큐, 컨설팅 배정, 사례 공개 요청, 연구 요청, 동의·보존 정책 초안
- 실제 개인정보는 일절 포함하지 않습니다.

`npm run seed:reset`은 실행 중 저장된 모든 데모 변경을 초기 합성 데이터로 되돌립니다.

## 내 정보·데이터

`내 정보·데이터`는 로그인한 사람의 참여기구 내 프로필 전용 화면입니다. 이름·선택형 연령대·직업·거주 지역과 함께 프로필 사진을 관리하며, 사진은 같은 테넌트에서 로그인한 구성원만 확인할 수 있습니다.

- 사진 등록: PNG, JPG, WebP / 2MB 이하. 등록 뒤 바로 프로필에 적용하며 기존 사진 파일은 교체 시 정리합니다.
- 비밀번호 변경과 데이터 내보내기·삭제/처리정지 요청은 화면을 단순하게 유지하기 위해 작은 `계정·데이터` 항목을 눌러 별도 대화상자에서 처리합니다.
- 사진은 로컬 MVP에서 `data/avatars/`에 저장됩니다. 실제 도입 전에는 악성 파일 검사, EXIF 처리 정책, 관리형 비공개 저장소, 보존·파기 기준을 확정해야 합니다.

## 테스트

```powershell
npm test
```

테스트는 다음을 확인합니다.

1. 일반위원이 다른 테넌트의 사용자·자료를 받지 않는지
2. 외부 검토자가 지정된 제안서만 보고 피드백할 수 있는지
3. 일반위원의 참석 응답·제안서 작성과 의장단의 최종 제출 기록이 가능한지
4. 간사가 조직 단위를 만들고 구성원을 배정하며, 외부 검토자는 이를 변경할 수 없는지
5. 운영사가 테넌트를 중지하면 해당 테넌트 접근이 차단되는지
6. 운영사 콘솔 API가 비운영사에게 차단되고, 합성 테넌트 생성·설정 변경이 가능한지
7. 연구·데이터 요청이 승인 대기 상태로만 기록되는지
8. 위원장이 초대 링크를 만들고 가입 신청을 승인한 뒤 신규 위원이 로그인하는지
9. 위원장이 회의를 수정하고 실제 출결·결정을 기록하며, 이슈·공지·자료를 등록하는지
10. 컨설팅 배정된 외부 검토자만 해당 제안서를 열람하는지
11. 위원장이 폴더를 만들고 회의 기록을 보관본으로 생성·갱신하며, 이동·기수 메모 이력이 남는지
11. 일반위원이 성과 리포트를 만들 수 없고, 위원장이 기간 리포트·다음 기수 권한 전환·인계 아카이브를 만들 수 있는지
12. 템플릿·체험 테넌트 구성원이 기관 계약·후원 좌석 활성화 전에는 운영 기록을 저장할 수 없는지
13. 공개 파일럿 문의가 운영사 접수함에만 저장되고, 운영사 관리자가 상태를 변경할 수 있는지
14. 계약형 테넌트가 활성화 전·이용 기간 밖에 운영 기록을 저장할 수 없는지
15. 동일 주소·식별자의 반복 로그인 실패가 일시 제한되는지
16. 위원장이 CSV·XLSX·HWP 자료를 검토 초안으로 올리고, 일반위원·다른 테넌트가 이를 볼 수 없으며, 선택한 명단 행만 최종 반영되는지

## 실제 파일럿 전 필수 사항

현재 MVP는 기능 검증용 로컬 서버이며, 실제 개인정보·공식 문서·기관 계정으로 운영할 수 있는 보안 완료 제품이 아닙니다. 실제 도입 전에 관리형 DB, 운영 환경의 비밀관리·HTTPS, 강한 인증, 개인정보 처리 역할·처리방침·보존 및 파기 절차, 보안 점검을 확정해야 합니다. 상세 목록은 [02_MVP_제품_명세와_구현_경계.md](./02_MVP_제품_명세와_구현_경계.md)를 확인하세요.
